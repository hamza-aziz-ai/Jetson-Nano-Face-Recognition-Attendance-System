# Threat model

The system holds biometric data (face photos, embeddings, snapshots, clips) of real people. In India this falls under the DPDP Act 2023. Gaps are listed plainly.

| Actor | Entry point | Worst realistic abuse | In place | Gap |
| --- | --- | --- | --- | --- |
| Someone on the LAN | Web page, port 8000 | View faces and attendance | Sign-in page (PBKDF2 hash) and a signed 12 h session cookie, HttpOnly (D-036), CSP `script-src 'self'` with no inline code, X-Frame-Options, nosniff; 10 failed logins in 15 min lock the client out without hashing | Plain HTTP: the password, session cookie and pages travel in clear; a stolen cookie works until it expires |
| A web page in the admin's browser | POST to the service controls | Stop recognition (cross-site request) | Per-process CSRF token in each form and a same-origin check on `Origin`/`Referer`; POST only; actions from a whitelist | None known |
| Someone with the web login | System page | Stop recognition, read recent log lines | The login itself; sudoers allows only start, stop and restart of `facepipe`; the web cannot stop itself; every action is logged | A stopped service records no attendance until started again (shown on every page) |
| Anyone on the LAN | `/register` (public) | Upload unwanted photos, flood storage | Only with a valid single-use invitation (128-bit, 48 h, stored as a hash); 4 MB per photo, 5 photos, 10 submissions per device per hour; photos decoded and re-encoded on the CPU before storing; nothing enrolled without admin approval | A person with a link could submit someone else's face; the admin's review is the check (no liveness) |
| A failed or partial enrollment | Gallery | Lose or corrupt everyone's templates | Candidate gallery built and checked in a staging folder; published by rename under the update lock; enroll never publishes when every photo failed | A crash between moving photos and the rename leaves photos without templates until the next enrollment |
| Someone with the web login | Cameras page | Learn a network camera's password | Pages show `user:•••`; logins only in `data/cameras.json` and `cameras.active` (0600); facepipe does not log the chosen address | The test command line holds the address while it runs (visible to local users of the device) |
| Anyone on the internet | `attendance.hamzaaziz.dev` (Cloudflare Tunnel) | Reach the sign-in page, guess the password | Sign-in page with a PBKDF2 hash, 10 failed attempts in 15 min lock the visitor out (`CF-Connecting-IP`, trusted only from this host); HttpOnly session cookie, `Secure` over HTTPS; no inbound port. Cloudflare Access removed at the owner's request (D-035 update) | The password is the only lock: it must be strong; a botnet with many addresses gets 10 tries per address; faces pass through Cloudflare when viewed remotely |
| A viewer (family member) | Website | Change settings, add users, see what they should not | Central `allowed()` on exact paths before any body or file is read; viewer gets 403 on People, Video upload, Users and every change, and System and Cameras without controls; menu hides them; sessions end at once on role change or deletion (D-040) | Viewers see everything read-only, including strangers' faces and clips (owner's choice) |
| Anyone on the internet | Sign-in page with many accounts | Guess a family member's weaker password; keep them out | 15-character minimum, PBKDF2, per-visitor limit, per-account pause up to 30 s after 5 failures, at most 2 hashes at once, same work for unknown names | Password only; a botnet with many addresses still gets tries; repeated failures can delay a real sign-in by up to 30 s |
| Someone who sees a set-password link | `/account/setup` | Take over a new account | 128-bit single-use link, 48 h, stored hashed, used up together with the password; a new link voids the old | Whoever gets the link first sets the password; send it privately |
| Someone with the web login | Video upload page | Crash or exploit facepipe with a crafted video; fill the disk | Login and form token; checked by `gst-discoverer` in a separate process; only H.264/H.265 (hardware decoder), at most 1080p and 30 min, limits re-checked while decoding; 3 waiting, 4 GB cap, 2 GB reserve; a video that was being processed at a crash is never retried (D-039) | The video is decoded inside the live process: a decoder bug can restart live recognition once per bad file (owner accepted) |
| Many clients at once | Web server | Exhaust memory or threads | At most 24 requests and 4 live viewers at a time; 30 s receive timeout; 4 KB request bodies; streamed downloads | None known |
| Anyone on the internet | RTSP, port 8554 | Watch the live camera in VLC or an NVR | Requests from addresses that are not private, link-local or loopback are refused 403 since v1.10.1, also through a port forward (D-041; bugs/rtsp-reachable-from-internet.md) | Not yet tested from mobile data |
| Someone on the LAN | RTSP, port 8554 | Watch the live camera | Separate login; server off without it | RTSP Basic auth is plain text on the network |
| Someone on the LAN | Path tricks in URLs | Read secrets or other files | Strict regexes for snapshot, evidence and photo paths; photos only for enrolled names | None known |
| Someone who can enroll | Gallery folder names | Script injection on the page | Names are HTML-escaped; tabs and newlines in names are skipped | Filesystem access to the device is already full control |
| Lookalike or photo of a person | Camera | False attendance | Match threshold 0.5 | No liveness check; threshold not tuned |
| Physical access | microSD card | Copy all faces and data | None | No disk encryption |
| Code contributor | Public repository | Ship malicious code | CI on every pull request; workflows from outside contributors need the maintainer's approval; the self-hosted runner only runs the Deploy workflow for published releases and manual dispatch, in the `production` environment | A pull request could edit a workflow to target the runner; the approval setting is the control, so never approve unreviewed workflow changes |
| Self-hosted runner | The Nano | Runs released code with the runner user's rights | Dedicated user with sudo only for restarting the two services | Not yet registered |
| The repository itself | GitHub | Leak secrets or faces | `.gitignore`; every push is scanned for IPs and secrets | Relies on the scan being run |

Data subject rights: to remove a person, delete their gallery folder, re-run enrollment, and delete their lines and snapshots from `data/` (see DATA.md).
